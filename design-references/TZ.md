## 1. Цель и границы проекта

### 1.1 Цель
CRM-система для продавца на Avito, закрывающая полный операционный цикл:
от создания заказа и закупки товара у поставщика — до возврата, расхода
и итоговой финансовой отчётности.

### 1.2 Что система ДЕЛАЕТ
- Учитывает заказы, их статусы и движение по жизненному циклу.
- Считает себестоимость, выручку, валовую и чистую прибыль по каждому заказу.
- Учитывает возвраты и корректно исключает их из финансовых показателей.
- Учитывает прочие расходы бизнеса по категориям.
- Хранит справочник контрагентов (поставщиков) и их статистику.
- Хранит справочник товаров, синхронизируемый из Avito API (только чтение
  номенклатуры/цен/статусов объявлений — НЕ заказов).
- Строит отчёты: P&L, по товарам, по контрагентам, по возвратам.
- Ведёт неизменяемый журнал изменений (audit log) по заказам.
- Разграничивает доступ между ролями Администратор и Менеджер.

### 1.3 Что система НЕ делает (явные границы — не реализовывать без подтверждения)
- **Не импортирует заказы из Avito автоматически.** Интеграция с Avito API
  ограничена номенклатурой (название, цена, статус объявления). Заказы
  создаются вручную пользователем CRM. Если возникнет соблазн "а давайте
  ещё подтянем заказы из Avito" — это выход за рамки ТЗ, требует отдельного
  обсуждения.
- Не мультитенантна — это CRM для одного бизнеса с несколькими
  пользователями (Админ/Менеджер), не SaaS для множества компаний.
- Не работает с доставкой/трекингом через API служб доставки — трек-номер
  это просто текстовое поле, вводимое вручную.
- Не считает налоги, не интегрируется с бухгалтерскими/налоговыми системами.
- Автоматическая синхронизация с Avito по расписанию — это явно описано
  в ТЗ как возможность для **будущего** расширения ("может быть расширена"),
  в первой версии реализуется только ручная синхронизация по кнопке.

## 2. Роли и права доступа

### 2.1 Роли

| Роль | Доступ |
|---|---|
| **Администратор** | Полный доступ ко всем разделам, включая системные настройки, управление пользователями, управление ролями |
| **Менеджер** | Заказы (создание/редактирование/просмотр), Возвраты (создание/редактирование/просмотр), Контрагенты (создание/редактирование/просмотр), Отчёты (только просмотр) |

### 2.2 Обязательное требование к реализации прав
Права доступа реализуются **на уровне сервера/API**, а не только скрытием
элементов интерфейса. Менеджер не должен иметь возможности выполнить
административное действие даже прямым вызовом API-эндпоинта, зная его адрес.
Каждый защищённый эндпоинт должен явно проверять роль вызывающего пользователя
перед выполнением операции.

Менеджеру недоступны: управление пользователями, управление ролями,
настройки интеграции с Avito API (сама кнопка синхронизации номенклатуры —
обычное действие, доступное Менеджеру, но настройки самой интеграции —
ключи API, параметры — только Админу), любые системные настройки.

### 2.3 Открытый вопрос (требует подтверждения перед реализацией)
- Нужна ли роль "Менеджер" с ограничением по конкретным контрагентам/товарам,
  или один Менеджер видит весь бизнес целиком? **По умолчанию: видит всё**,
  ограничение только по разделам, не по данным внутри раздела.

**Дополнение по дизайн-макетам (раздел 13):** карточки заказов и возвратов
показывают атрибут **«Цвет»** товара (например "Белый", "Чёрный",

бизнес-логикой — реализуется как текстовое поле `variant` на уровне Order
(не Product), так как один и тот же товар-номенклатура может продаваться
в разных цветах в разных заказах:
- `Order.variant` (string, опционально) — например "Белый", "Чёрный".

Не вводить отдельную сущность ProductVariant с собственным складским учётом
в MVP — в макетах нет признаков раздельного учёта остатков по цвету,
только отображение атрибута в карточке.

**Важное архитектурное решение, требующее подтверждения у заказчика
перед реализацией:** `salePrice` хранится на Product и копируется в Order
в момент создания заказа (поле `Order.salePriceAtOrder`), а не читается
"вживую" из Product при каждом расчёте. Это нужно, потому что цена товара
в Avito может измениться после того, как заказ уже был оформлен по старой
цене — финансовые показатели прошлых заказов не должны "задним числом"
пересчитываться из-за изменения цены товара сегодня. Цена продажи
**подставляется автоматически** при выборе товара в заказе, но должна быть
**редактируемой** на уровне конкретного заказа (менеджер мог дать скидку).

#### 3.6.1 Статус возврата (дополнение по дизайн-макетам — раздел 13)
Макет экрана "Возвраты" показывает фильтр и значения статуса самой записи
возврата, не зафиксированные явно как отдельный enum в исходном тексте ТЗ
(раздел 0): `На возврате`, `Возвращен`, `Отменен`.

```
ReturnStatus:
  RETURNING  — "На возврате" — возврат оформлен, товар в пути обратно
  RETURNED   — "Возвращен"   — товар фактически вернулся на склад
  CANCELLED  — "Отменен"     — оформленный возврат не состоялся
```

**Связанный эффект на статус заказа:** если Return переходит в
`CANCELLED`, связанный Order должен вернуться в статус `RECEIVED`
(возврат отменён — товар остался у клиента, деньги по заказу снова
учитываются в прибыли). Это расширяет диаграмму переходов статуса заказа
из раздела 4.2 — см. обновление там же.

**Связь Return ↔ Order:** возврат не существует без заказа. Создание
возврата для заказа должно автоматически переводить статус связанного
заказа в "На возврате", а подтверждение фактического возврата товара —
в "Возвращен" (см. раздел 4 про статусы и раздел 7 про побочные эффекты).

## 4. Статус-модель заказа

### 4.1 Статусы (enum OrderStatus)

```
ACCEPTED      — "Принят"      — клиент оформил заказ
SHIPPED       — "Отправлен"   — заказ передан в доставку
RECEIVED      — "Получен"     — клиент получил товар
RETURNING     — "На возврате" — товар находится в процессе возврата
RETURNED      — "Возвращен"   — товар фактически вернулся на склад
```

### 4.2 Диаграмма разрешённых переходов

```
ACCEPTED ──────► SHIPPED ──────► RECEIVED
                    │                │  ▲
                    │                ▼  │ (Return.status → CANCELLED)
                    └──────────► RETURNING ──────► RETURNED
```

Пояснение по неочевидным переходам:
- `SHIPPED → RETURNING` допустим: товар мог быть возвращён в процессе
  доставки, не доходя до клиента (отказ при получении).
- `RECEIVED → RETURNING` — основной кейс возврата: клиент получил, потом
  решил вернуть.
- `ACCEPTED → RETURNING` — НЕ допускается. Если заказ отменён до отправки,
  это не "возврат" в терминах ТЗ — для такого случая нет отдельного статуса
  в исходном документе; **зафиксировать как открытый вопрос** (см. 4.4),
  по умолчанию реализовать как возможность удалить/отменить заказ в статусе
  ACCEPTED без перехода через статус возврата.
- `RETURNING → RECEIVED` — **допускается**, но только как побочный эффект
  отмены самой записи Return (см. 3.6.1), а не как прямое ручное действие
  над заказом. Дизайн-макет экрана "Возвраты" показывает статус возврата
  "Отменён" — если пользователь отменяет оформленный возврат, заказ
  логически возвращается в "Получен" (товар остался у клиента). Прямого
  UI-перехода Order: RETURNING → RECEIVED без отмены связанного Return
  быть не должно — это всегда происходит только через смену
  `Return.status` на `CANCELLED`.
- Переход `RETURNING → RECEIVED` напрямую (без записи Return или без
  смены её статуса на CANCELLED) не описан ни в исходном тексте ТЗ, ни
  в макетах — **не реализовывать**.

### 4.3 Жёсткая привязка переходов статуса к финансовым последствиям

Это формализация ключевого правила ТЗ ("только после перевода заказа в
статус «Получен» выручка и прибыль должны попадать в финансовые отчёты" +
"возвраты должны исключаться из прибыли после перевода в статус «Возвращен»").

| Переход | Финансовый эффект |
|---|---|
| `* → RECEIVED` | Заказ начинает учитываться в выручке/прибыли всех отчётов и Dashboard |
| `RECEIVED → RETURNING` | Заказ **немедленно** прекращает учитываться в выручке/прибыли (даже до завершения возврата — товар уже не у клиента, бизнес не может считать эти деньги полученными для целей прибыли) |
| `RETURNING → RETURNED` | Подтверждение факта возврата; финансово ничего не меняется относительно предыдущего шага (уже исключён), но создаётся запись Return со статистикой по причинам возврата |
| `SHIPPED → RETURNING` (без прохождения RECEIVED) | Заказ никогда не учитывался в выручке (был ACCEPTED/SHIPPED), его и не нужно "исключать" — просто не учитывать |

**Важно для реализации:** "исключение из прибыли" не должно реализовываться
как фильтр `WHERE status = 'RECEIVED'` исключительно на уровне SQL-запроса
отчёта (хотя на чтении это и корректно) — оно должно быть осмыслено
архитектурно: если используется денормализованный кэш (FinancialOperation
или агрегаты на Counterparty/Product), переход в RETURNING/RETURNED должен
**инвалидировать или явно реверсировать** ранее учтённую сумму, а не
оставлять "протухшие" цифры в кэше. Это требование — основной источник
багов в подобных системах, проверять отдельно тест-кейсом.

### 4.4 Открытые вопросы по статусам (зафиксировать, спросить перед реализацией доп. функциональности)
- Нужен ли отдельный статус/механизм отмены заказа до отправки (`CANCELLED`)?
  В тексте ТЗ такого статуса нет. По умолчанию: не реализовывать отдельный
  статус, считать, что заказ в ACCEPTED можно удалить (мягко — деактивировать,
  не физически стирать, чтобы не плодить дыры в orderNumber и не терять
  audit log).
- Частичный возврат (вернули 2 из 5 единиц товара) — в ТЗ не описан,
  модель Return сейчас на уровне всего заказа. Не реализовывать частичные
  возвраты в MVP без отдельного согласования.

## 5. Бизнес-правила (нормативный список — каждое реализуется и тестируется отдельно)

**BR-1.** В выручку, себестоимость и прибыль любого отчёта или
карточки Dashboard попадают **только** заказы со статусом `RECEIVED`
на момент построения отчёта/дашборда.

**BR-2.** Заказ со статусом `RETURNING` или `RETURNED` **исключается**
из всех финансовых показателей, даже если ранее (будучи в `RECEIVED`)
уже был учтён в каком-либо отчёте за прошлый период. Финансовые показатели
всегда отражают **текущее** состояние статусов, а не "замороженное" на
момент прошлого просмотра.

**BR-3.** Все производные финансовые показатели (выручка, себестоимость,
валовая/чистая прибыль, маржинальность) вычисляются **одной и той же**
функцией/модулем расчёта во всех местах системы (Dashboard, таблица
заказов, отчёты). Дублирование формул в разных компонентах кода —
запрещено, выносится в общий сервис (см. раздел 7.1).

**BR-4.** Все финансовые показатели пересчитываются автоматически при
любом изменении влияющих данных (изменение статуса, изменение цены/
количества/расходов по заказу, добавление расхода, оформление возврата).
Пользователь никогда не должен видеть устаревшие цифры и не должен
вручную запускать "пересчёт".

**BR-5.** Записи AuditLog никогда не удаляются и не редактируются
(append-only). Любое изменение полей заказа создаёт новую запись
AuditLog, а не модифицирует существующую.

**BR-6.** Синхронизация номенклатуры с Avito выполняется только по явному
действию пользователя (кнопка "Обновить из Avito"). Система не делает
фоновых автоматических вызовов к Avito API в MVP.

**BR-7.** Права доступа Менеджера и Администратора проверяются на сервере
для каждого защищённого действия независимо от UI.

**BR-8.** Изменение статуса заказа на `RETURNING` обязательно создаёт
(или требует создания) связанной записи `Return`. Заказ не может
находиться в статусе `RETURNING`/`RETURNED` без соответствующей записи
о возврате — это нужно для целостности отчёта "по возвратам".

**BR-9.** Статус связанного заказа всегда синхронизирован со статусом
записи Return (см. 3.6.1, раздел 4.2): `Return.status = RETURNING` →
`Order.status = RETURNING`; `Return.status = RETURNED` →
`Order.status = RETURNED`; `Return.status = CANCELLED` →
`Order.status = RECEIVED`. Изменение статуса Return и соответствующее
изменение статуса Order выполняются в одной транзакции — не должно
существовать момента, когда они расходятся.

## 6. Разделы системы и их детализация

### 6.1 Dashboard (Главная страница)

#### 6.1.0 Верхний фильтр (дополнено по дизайн-макету, раздел 13)
Под заголовком — выбор даты (по умолчанию текущий день) и фильтр **"Все
города"**. В исходном тексте ТЗ фильтра по городу на главной странице не
было (там был только список конкретных KPI-карточек) — макет показывает,
что весь Dashboard может быть отфильтрован по городу получателя
(`Order.destinationCity`), аналогично фильтру в разделе "Заказы" (6.2.2).
При выборе конкретного города все KPI-карточки, "Последние заказы",
"Топ товаров" и "Финансы за месяц" пересчитываются с учётом фильтра.

#### 6.1.1 KPI-карточки (верхний блок)
| Карточка | Источник расчёта |
|---|---|
| Продажи сегодня | COUNT(Order) WHERE status = RECEIVED AND статус изменён на RECEIVED сегодня* |
| Выручка сегодня | SUM(revenue) по тому же набору заказов |
| Прибыль сегодня | SUM(netProfit) по тому же набору заказов |
| Продажи за неделю | COUNT(Order) WHERE status = RECEIVED за последние 7 дней* |
| Прибыль за неделю | SUM(netProfit) за тот же период |

\* **Открытый вопрос, требующий решения до реализации:** "за день/неделю"
считается по дате **перехода в статус RECEIVED** (т.е. фактической даты
получения клиентом) или по `orderDate` (дате оформления заказа)? Это
разные и обе осмысленные интерпретации. **По умолчанию реализовать по
дате перехода в RECEIVED** (нужно отдельное поле `receivedAt` на Order,
заполняемое при смене статуса), так как это ближе к кассовому методу учёта
и соответствует формулировке "заказов, **полученных** сегодня" из ТЗ.
Дату создания заказа (`orderDate`) использовать для фильтра в разделе
"Заказы", не для KPI-карточек Dashboard.

#### 6.1.2 Последние заказы
Таблица последних 10 заказов (по `createdAt` desc), независимо от статуса.
Поля: миниатюра товара (`Product.imageUrl`, см. 3.3), Товар, Трек-номер,
Сумма продажи (revenue), Прибыль (netProfit), Статус. (Поле "Дата" из
исходного текста ТЗ в макете визуально не выделено отдельной колонкой на
этом конкретном виджете — оставить доступным при открытии полной таблицы
заказов по ссылке "Все заказы".)

#### 6.1.3 Топ товаров
Список Product, отсортированный по суммарной прибыли (убывание),
агрегированной **только** по заказам в статусе RECEIVED.
Поля: порядковый номер места в рейтинге, Товар, Прибыль (в компактном
виде на Dashboard — по макету показаны только название и прибыль;
количество продаж и выручка доступны в полном отчёте по товарам, 6.7.3).

#### 6.1.4 Финансы за месяц
Карточки за текущий календарный месяц: Выручка, Расходы (сумма всех
Expense плюс Order.logisticsCost/commissionCost/otherCosts, см. 3.7.1),
Чистая прибыль. (В макете блок называется "Финансы за месяц" и показывает
именно эти три карточки; отдельная карточка "Закупки" из исходного текста
ТЗ в макете не выделена отдельно — закупки входят в расчёт себестоимости,
который уже учтён в Чистой прибыли. Сохранить возможность показать
"Закупки" отдельной карточкой опционально, не как обязательный элемент.)

#### 6.1.5 Быстрые действия
Кнопки-шорткаты, открывающие соответствующие формы/модалки:
➕ Новый заказ · 🔍 Найти заказ · ↩ Возврат · 💰 Расход.
(Порядок и краткие подписи кнопок — по макету; пятая кнопка "Обновить
номенклатуру Avito" из исходного текста ТЗ в макете главного экрана не

- Поиск по номенклатуре (autocomplete по Product.name)
- Название товара — подставляется при выборе из поиска
- Вариант/цвет (`Order.variant`, см. 3.3) — текстовое поле, заполняется
  вручную при создании заказа (дополнено по дизайн-макету, раздел 13 —
  в исходном тексте ТЗ этого поля не было)
- Цена продажи — подставляется автоматически из `Product.salePrice`,
  редактируема пользователем перед сохранением (сохраняется как
  `Order.salePriceAtOrder`, см. 3.5/3.3)

**Блок "Логистика":**
- Трек-номер (обязательное, текст)
- Количество (обязательное, целое > 0)
- Дата заказа (обязательное)
- Дата отправки (необязательно при создании; заполняется/редактируется
  при переходе в статус "Отправлен")
- Город получателя (обязательное)

**Блок "Закупка":**
- Контрагент (поставщик) — выбор из справочника Counterparty, либо
  создание нового контрагента "на лету" из этой же формы
- Закупочная стоимость за единицу (обязательное, decimal)
- Комментарий (необязательно)

После заполнения всех блоков — расчётные поля (выручка, себестоимость,
прибыль, маржинальность) показываются как **предпросмотр в реальном
времени** на основе введённых данных, ещё до сохранения заказа.

#### 6.2.4 Изменение статуса заказа
- Доступные следующие статусы — только согласно диаграмме переходов
  (раздел 4.2); UI не должен предлагать невозможные переходы.
- Переход в `SHIPPED` — предлагает заполнить/подтвердить дату отправки.
- Переход в `RETURNING` — обязательно открывает форму создания Return
  (см. 6.3) с предзаполненными Товар/Трек-номер/Дата отправки из заказа;
  без заполнения причины возврата переход не завершается.
- Каждое изменение статуса создаёт запись AuditLog (BR-5) и пересчитывает
  все зависимые финансовые показатели (BR-4).

### 6.3 Раздел "Возвраты"

#### 6.3.1 Поиск и фильтры (дополнено по дизайн-макету, раздел 13)
Поиск: по трек-номеру, по товару.
Фильтры: по статусу возврата (см. 3.6.1), по дате, по товару, по причине
возврата. Дополнительно — горизонтальные вкладки-чипы быстрого фильтра по
статусу: "Все" / "На возврате" / "Возвращён" / "Отменён", как показано
в макете.

#### 6.3.2 Карточка возврата
Поля: Товар (с миниатюрой изображения и вариантом/цветом — см. 3.3),
Трек-номер, Статус (см. 3.6.1), Дата отправки, Дата возврата (если
применимо), Причина возврата (вводится вручную, свободный текст — список
причин в ТЗ не зафиксирован как фиксированный enum, реализовать как
текстовое поле; если потребуется аналитика "по причинам" в будущем —
потребуется ввести enum отдельно, сейчас не требуется), Комментарий.

#### 6.3.3 Связь со статусом заказа
Создание Return со статусом `RETURNING` → `Order.status = RETURNING`.
Подтверждение фактического возвращения товара на склад (перевод Return
в `RETURNED`, заполнение `Return.returnDate`) → `Order.status = RETURNED`.
Отмена возврата (перевод Return в `CANCELLED`) → `Order.status = RECEIVED`.
См. BR-8, BR-9.

#### 6.3.4 Сводные показатели (по дизайн-макету)
Под списком возвратов — сводная строка: Всего возвратов, На возврате
(количество в статусе RETURNING), Возвращено (количество в статусе
RETURNED). Считается по текущему фактическому распределению статусов,
не кэшируется отдельно от самих записей Return.

### 6.4 Раздел "Контрагенты"

#### 6.4.1 Карточка контрагента
Поля: Название, Контактные данные, Комментарий.

#### 6.4.2 Статистика контрагента (вычисляемая, не редактируемая руками)
- Количество заказов — всего заказов, где этот контрагент указан как поставщик
- Количество закупок — здесь требуется уточнение: совпадает ли с
  "количество заказов" или считается отдельно (например, по партиям
  закупки)? **По умолчанию в MVP считать равным количеству заказов**,
  где этот контрагент — поставщик, так как отдельной сущности "Закупка"
  вне контекста заказа в модели данных ТЗ не описано.
- Общая сумма закупок — SUM(purchasePricePerUnit × quantity) по всем
  заказам этого контрагента, **независимо от статуса заказа** (закупка
  как факт расхода произошла независимо от того, вернул ли клиент товар)
- Общая выручка — SUM(revenue) **только** по заказам в статусе RECEIVED
  (BR-1)
- Общая прибыль — SUM(netProfit) **только** по заказам в статусе RECEIVED

### 6.5 Раздел "Номенклатура"

#### 6.5.1 Поля
Название, Цена продажи, Ссылка на объявление, Статус объявления.

#### 6.5.2 Функция "Обновить из Avito"
- Запрос к Avito API за текущим списком объявлений пользователя.
- Сопоставление с существующими записями Product по `avitoItemId`.
- Обновление полей `name`, `salePrice`, `avitoListingStatus`,
  `avitoListingUrl`, `lastSyncedAt` для существующих; создание новых
  Product для объявлений, которых ещё нет в базе.
- **Не удалять** Product при синхронизации, даже если объявление снято
  с Avito (история заказов ссылается на этот товар) — только обновлять
  `avitoListingStatus` на статус "снято"/неактивно.
- Выполняется только вручную нажатием кнопки (BR-6); показывать
  пользователю результат синхронизации (сколько обновлено/добавлено,
  ошибки при сбое).

### 6.6 Раздел "Расходы"

Поля записи: Дата, Категория (enum из 3.7.1), Название/заголовок расхода
(`title`, см. 3.7.2), Сумма, Способ оплаты (`paymentMethod`, см. 3.7.2),
Комментарий.

Список всех расходов с фильтрацией по дате, категории и **способу оплаты**
(дополнено по дизайн-макету, раздел 13 — в исходном тексте ТЗ фильтра
по способу оплаты не было).

**Сводка по категориям** над списком (по макету): карточки "Расходы за
месяц" с общей суммой и разбивкой по всем 7 категориям из 3.7.1 —
визуально сгруппированные KPI-плитки, а не только список записей.

**Сводка под списком:** Всего расходов за период, Средний расход в день
(= сумма расходов за период / количество дней в периоде).

**Важно:** этот раздел — для расходов, **не привязанных к конкретному
заказу**. Расходы, относящиеся к конкретному заказу (логистика, комиссия),
вводятся в самом заказе (поля `logisticsCost`, `commissionCost`,
`otherCosts`) и не должны задваиваться записью в Expense — см. 3.7.1.

### 6.7 Раздел "Отчёты"

#### 6.7.0 Структура экрана (дополнено по дизайн-макету, раздел 13)
Макет показывает раздел "Отчёты" как **набор вкладок** одного экрана,
а не отдельные несвязанные страницы:

```
[ Дашборд ] [ P&L ] [ Товары ] [ Контрагенты ] [ Возвраты ]
```

— с общим выбором периода (диапазон дат) и кнопкой "Фильтры", применимыми
ко всем вкладкам. Это уточняет структуру раздела относительно исходного
текста ТЗ, где KPI и под-отчёты были описаны как единый плоский список —
теперь они явно разнесены по вкладкам, при этом вкладка "Дашборд"
объединяет KPI-карточки и визуализации (6.7.1–6.7.1.3), а остальные
вкладки соответствуют под-отчётам 6.7.2–6.7.5.

#### 6.7.1 Вкладка "Дашборд" — KPI-карточки за период
Выручка, Прибыль, Количество заказов, Средний чек (= Выручка / Количество
заказов, только RECEIVED), Возвраты (количество заказов в RETURNED — в
макете отображается как абсолютное число с подписью "% от всех заказов"
рядом), Маржа % (= валовая или чистая прибыль / выручка — **уточнить
у заказчика, какая маржа имеется в виду**; по умолчанию использовать
маржинальность по чистой прибыли, как наиболее консервативный показатель).

**Сравнение с прошлым периодом (дополнено по макету):** каждая из
KPI-карточек дополнительно показывает изменение в процентах относительно
предыдущего периода той же длины (например, выбран период 01.06–23.06 —
сравнение идёт с периодом 09.05–31.05 той же продолжительности,
непосредственно предшествующим выбранному). Этого расчёта не было в
исходном тексте ТЗ; реализуется как дополнительный вычисляемый показатель
поверх той же агрегирующей функции (BR-3) — два вызова с разными
диапазонами дат, не отдельная формула.

#### 6.7.1.1 График динамики (дополнено по макету)
Линейный график "Динамика за период": две линии — Выручка и Прибыль —
по дням (с возможностью переключения гранулярности, в макете показан
переключатель "По дням"). Данные — те же агрегаты, что и в KPI-карточках,
разбитые по дням периода.

#### 6.7.1.2 Структура расходов (дополнено по макету)
Круговая диаграмма расходов за период с разбивкой по категориям из 3.7.1
(Закупка товара, Логистика, Реклама, Комиссии, Упаковка, Прочие), с
указанием суммы и процента каждой категории от общих расходов. Источник
данных — тот же, что и для P&L-отчёта (6.7.2), просто визуализированный
по категориям, а не по форме "Выручка минус статьи".

#### 6.7.1.3 Заказы по статусам (дополнено по макету)
Круговая диаграмма распределения **всех** заказов за период (не только
RECEIVED) по статусам (`ACCEPTED`, `SHIPPED`, `RECEIVED`, `RETURNING`,
`RETURNED`) с количеством и процентом каждого статуса. Это единственное
место в разделе "Отчёты", где статусы, отличные от RECEIVED, явно
визуализируются как часть аналитики, а не просто исключаются — полезно
для контроля "зависших" заказов в промежуточных статусах.

#### 6.7.2 Вкладка "P&L"
```
Выручка
− Себестоимость товаров
− Логистика
− Комиссии Avito
− Реклама
− Прочие расходы
= Чистая прибыль
```
Реализационное уточнение: "Логистика" и "Комиссии Avito" в этой формуле
должны суммировать **оба** источника — поля на заказах (`logisticsCost`,
`commissionCost`) и записи Expense с соответствующими категориями
(`LOGISTICS`, `AVITO_COMMISSION`), без задвоения (см. 3.7.1). "Реклама" и
"Прочие расходы" берутся из Expense (категории `ADVERTISING`, `OTHER` +
`SALARY` + `PACKAGING` — в макете эти две категории не выводятся отдельной
строкой в самом P&L, а агрегируются в "Прочие расходы"; **по умолчанию
для P&L-отчёта: следовать макету и сворачивать `SALARY`+`PACKAGING`+`OTHER`
в одну строку "Прочие расходы"**, при этом детальная разбивка по всем
7 категориям остаётся доступна на вкладке "Дашборд" через диаграмму
6.7.1.2 и в разделе "Расходы" — детализация не теряется, просто P&L
показывает её свёрнутой согласно макету).

#### 6.7.3 Вкладка "Товары"
Товар, Продано (количество, RECEIVED), Выручка, Прибыль. В макете на
вкладке "Дашборд" уже есть превью этого отчёта ("Прибыль по товарам" —
топ-5 с миниатюрами) со ссылкой "Все товары" — полноценная таблица
открывается на вкладке "Товары".

#### 6.7.4 Вкладка "Контрагенты"
Контрагент, Закуплено (сумма закупок, см. 6.4.2), Продано (выручка по
заказам этого контрагента, RECEIVED), Прибыль.

#### 6.7.5 Вкладка "Возвраты"
Товар, Количество возвратов, Процент возвратов (= возвраты этого товара /
все заказы этого товара, прошедшие через RECEIVED).

### 6.8 История изменений (Audit Log) — UI

Отдельный просматриваемый журнал (доступен Администратору; вопрос
видимости Менеджеру — не зафиксирован в ТЗ, по умолчанию: только
Администратору, так как явно не указан в списке доступов Менеджера).
Отображение в формате из примера ТЗ:

```
Дата: 15.07.2026
Поле: Статус заказа
Изменение: Принят → Отправлен
Пользователь: Иван
```

Фильтрация минимально — по заказу (открыть историю конкретного заказа из
карточки заказа) и общий журнал с фильтром по дате/пользователю.

## 7. Архитектурные требования к реализации

### 7.1 Единый модуль финансовых расчётов
Все формулы из раздела 3.5 реализуются как чистые функции в одном модуле
(например `lib/finance/calculations.ts`), без побочных эффектов, без
прямых обращений к БД внутри самих формул. Этот модуль:
- Покрывается unit-тестами на 100% веток (включая edge case `revenue = 0`
  для `marginPercent`, отрицательные значения, дробные количества — если
  они допустимы, нулевые расходы).
- Используется **и только используется** Dashboard-сервисом, сервисом
  таблицы заказов и сервисом отчётов. Любой второй независимый расчёт той
  же формулы где-либо в коде — архитектурная ошибка.

### 7.2 Пересчёт при изменении статуса (реализация BR-2, BR-4)
Рекомендуемый подход: при любом изменении `Order.status` или денежных
полей заказа — выполнять в одной транзакции:
1. Обновление самого заказа.
2. Запись в AuditLog.
3. Если есть денормализованные агрегаты (FinancialOperation либо
   материализованные показатели на Product/Counterparty) — инвалидация
   или прямой пересчёт затронутых агрегатов в той же транзакции.

Если решено **не** использовать денормализацию и считать агрегаты "на
чтение" прямым запросом к Order/Return/Expense с фильтром по статусу —
это допустимо и даже предпочтительно для MVP с умеренным объёмом данных,
но тогда пункт 3 выше не нужен, а все отчётные запросы обязаны фильтровать
по актуальному `status = RECEIVED` непосредственно в запросе, без кэша.
**Решение зафиксировать и придерживаться его во всех отчётах одинаково.**

### 7.3 Схема БД — статус как enum
`OrderStatus` реализуется как enum на уровне БД (Postgres enum или
проверочное ограничение CHECK), не как свободная строка — чтобы исключить
опечатки и невалидные значения на уровне данных, а не только валидацией
в коде приложения.

### 7.4 Безопасность доступа
Каждый API-роут, изменяющий или читающий данные, защищён middleware,
проверяющим роль пользователя из сессии. Список административных-только
действий явно зафиксирован в одном месте конфигурации (не разбросан по
условиям `if role === 'ADMIN'` в произвольных местах кода).

### 7.5 Append-only AuditLog
См. 3.8 — рассмотреть ограничение на уровне БД (права доступа роли
приложения к таблице), а не только отсутствие UPDATE/DELETE-эндпоинтов
в API.

### 7.6 Интеграция с Avito API
- Реализуется как отдельный сервисный модуль с понятным интерфейсом
  (например `syncAvitoListings()`), скрывающим детали HTTP-вызовов к
  Avito от остального приложения.
- Хранение ключей/токенов доступа к Avito API — в переменных окружения,
  не в БД в открытом виде; настройка доступна только Администратору.
- Обработка ошибок синхронизации (недоступность API, истёкший токен,
  rate limit) — синхронизация не должна "тихо" завершаться с частичным
  результатом без сообщения пользователю, что именно пошло не так.

## 8. Нефункциональные требования

- **Локализация:** интерфейс на русском языке (термины ТЗ — "Принят",
  "Отправлен" и т.д. — использовать как есть в UI, не переводить на
  английский даже при английских именах enum в коде).
- **Валюта:** рубли (₽), без поддержки мультивалютности в MVP.
- **Часовой пояс:** все даты — в часовом поясе бизнеса (уточнить у
  заказчика конкретный часовой пояс при настройке проекта; по умолчанию
  Europe/Moscow).
- **Производительность:** Dashboard должен загружаться без видимых
  задержек при объёме до нескольких тысяч заказов — учитывать индексацию
  по `status`, `orderDate`, `receivedAt`, `trackingNumber`.
- **Адаптивность:** интерфейс должен корректно работать на десктопе
  (основной режим использования) — мобильная адаптация не первый приоритет,
  но не должна быть полностью нерабочей.

## 9. Тестирование (минимальный обязательный набор)

1. **Финансовые формулы** (раздел 3.5) — unit-тесты для каждой формулы,
   включая нулевую выручку, нулевые расходы, дробные/целые количества.
2. **BR-1/BR-2** — интеграционный тест: заказ в RECEIVED учитывается в
   отчёте; тот же заказ, переведённый в RETURNING, немедленно исчезает
   из показателей следующего запроса отчёта без ручного пересчёта.
3. **Статус-машина** — тест, что недопустимые переходы (например,
   ACCEPTED → RETURNED напрямую) блокируются на уровне сервиса, не только UI.
4. **AuditLog** — тест, что изменение статуса создаёт запись лога с
   корректными старым/новым значением; тест, что DELETE/UPDATE по таблице
   AuditLog недоступен через API ни одной роли.
5. **Права доступа** — тест, что Менеджер получает 403 при попытке вызвать
   административный эндпоинт напрямую (не через UI).
6. **Контрагент/товар — статистика** — тест агрегатов из 6.4.2/6.7.3 на
   наборе заказов с разными статусами (включая RETURNED), чтобы убедиться,
   что закупки считаются независимо от статуса, а выручка/прибыль — только
   по RECEIVED.

## 10. Дизайн и UI — общий принцип

Референсы и примеры качественного интерфейса добавлены заказчиком
непосредственно в директорию проекта (`/design-references`) и являются
приоритетным источником визуального направления — стиль, типографика,
плотность интерфейса и компоновка должны ориентироваться на них, а не на
типовые дефолты UI-библиотек. Большая часть документа (разделы 1–9)
описывает только **информационную структуру** экранов (что на них должно
быть) — её детализация по конкретным макетам собрана в разделе 13.

## 11. Глоссарий терминов ТЗ → код

| Термин в ТЗ (рус.) | Имя в коде | Комментарий |
|---|---|---|
| Принят | `ACCEPTED` | статус заказа |
| Отправлен | `SHIPPED` | статус заказа |
| Получен | `RECEIVED` | статус заказа |
| На возврате | `RETURNING` | статус заказа / статус возврата |
| Возвращен | `RETURNED` | статус заказа / статус возврата |
| Отменен | `CANCELLED` | статус возврата (см. 3.6.1) |
| Себестоимость | `costOfGoods` | = закупочная цена × количество |
| Валовая прибыль | `grossProfit` | = выручка − себестоимость |
| Чистая прибыль | `netProfit` | = выручка − себестоимость − логистика − комиссии − прочие расходы |
| Маржинальность | `marginPercent` | = валовая прибыль / выручка × 100 |
| Контрагент | `Counterparty` | поставщик товара, НЕ покупатель |
| Номенклатура | `Product` | справочник товаров, синхронизируется из Avito |
| Цвет / Вариант | `Order.variant` | атрибут конкретного заказа, см. 3.3 |
| Способ оплаты | `Expense.paymentMethod` | см. 3.7.2 |

## 12. Список открытых вопросов (свод из разделов выше — обсудить с заказчиком до или во время реализации соответствующего модуля)

1. KPI "за день/неделю" на Dashboard — по дате перехода в RECEIVED или по
   дате создания заказа? (раздел 6.1.1) — *рабочее решение принято: по
   дате перехода в RECEIVED.*
2. Нужен ли статус/механизм отмены заказа до отправки (раздел 4.4)?
   — *рабочее решение: мягкое удаление ACCEPTED-заказа без статуса CANCELLED.*
3. Частичные возвраты — поддерживать ли в MVP? (раздел 4.4)
   — *рабочее решение: нет, не в MVP.*
4. "Количество закупок" у контрагента — равно ли "количеству заказов"?
   (раздел 6.4.2) — *рабочее решение: да, равно, в MVP.*
5. "Маржа %" в KPI отчётов — по валовой или по чистой прибыли? (раздел 6.7.1)
   — *рабочее решение: по чистой прибыли.*
6. Видимость раздела Audit Log Менеджеру? (раздел 6.8)
   — *рабочее решение: только Администратору.*
7. Денормализация финансовых агрегатов (FinancialOperation) vs расчёт "на
   чтение" — архитектурное решение, см. раздел 7.2, выбирается на этапе
   проектирования схемы и затем фиксируется как стандарт для всей системы.
8. Часовой пояс бизнеса для дат — подтвердить Europe/Moscow или другой.
9. "Закупки" как отдельная карточка на Dashboard (раздел 6.1.4) — в макете
   не показана отдельно, входит в расчёт прибыли. Нужна ли она отдельной
   карточкой всё же, или достаточно того, что есть в макете?
   — *рабочее решение: не выводить отдельной карточкой, следуя макету.*
10. Кнопка "Обновить номенклатуру Avito" — в макете не вынесена на
    Dashboard в "Быстрые действия" (раздел 6.1.5). Подтвердить, что её
    место — только в разделе "Номенклатура".
    — *рабочее решение: да, оставить только в "Номенклатуре".*
11. `Order.variant` (цвет/вариант товара, раздел 3.3) — вводится оператором
    свободным текстом, или должен подтягиваться из ограниченного списка
    вариантов, заданных для конкретного товара? В макете показаны
    стандартные значения ("Белый", "Чёрный", "Натуральный титан"), похожие
    на варианты цвета у электроники — возможно, источник истины для списка
    цветов — сам Avito (объявления часто публикуются отдельно на каждый
    цвет). Уточнить у заказчика реальный сценарий.
    — *рабочее решение: свободное текстовое поле в MVP, без отдельного
    справочника вариантов.*
12. P&L-отчёт в макете сворачивает Зарплаты/Упаковку/Прочее в одну строку
    "Прочие расходы" (раздел 6.7.2) — подтвердить, что детализация по этим
    трём категориям нужна заказчику только на вкладке "Дашборд"
    (диаграмма "Структура расходов") и в разделе "Расходы", а не в самом
    P&L.
    — *рабочее решение: да, следовать макету, P&L сворачивает эти три
    категории.*
13. Сравнение KPI "к прошлому периоду" в процентах (раздел 6.7.1) — нужно
    подтвердить точную логику выбора периода сравнения (предыдущий период
    той же длины, аналогичный период прошлого месяца/года, или что-то
    ещё) — в макете виден только сам процент без явного указания базы
    сравнения.
    — *рабочее решение: предыдущий период той же длины, непосредственно
    предшествующий выбранному.*

Каждое "рабочее решение" выше — это решение по умолчанию, принятое для
того, чтобы не блокировать разработку, а не финальное согласованное
решение заказчика. При реализации соответствующего раздела стоит свериться
с заказчиком, особенно по пунктам 1, 2, 5, 11, 13 — они влияют на видимые
пользователю цифры или на сценарии ввода данных.

## 13. Дизайн-референсы — детальный разбор по экранам

Заказчик предоставил 5 мокапов (хранятся в `/design-references`),
покрывающих ключевые экраны системы. Этот раздел — единая сводная
таблица того, что в этих макетах есть **сверх** исходного текста ТЗ
(раздел 0), с указанием, где в документе это уже учтено. Используется
как чек-лист при реализации каждого экрана: при открытии любого из пяти
макетов агент должен пройти по соответствующей строке этой таблицы и
убедиться, что все перечисленные элементы реализованы.

### 13.1 Экран "Главная" (Dashboard)
- Тёмная тема (в отличие от остальных четырёх экранов — светлая тема).
  **Указывает, что в системе предполагается переключение между светлой и
  тёмной темой**, либо что Dashboard стилистически отличается от
  остального приложения — уточнить у заказчика финальное решение по теме;
  до уточнения реализовать переключение темы (light/dark) как глобальную
  настройку приложения, единую для всех экранов, беря тёмную тему за
  основу палитры для дальнейшей адаптации остальных экранов, либо наоборот —
  решает дизайнер на основе совокупности референсов.
- Фильтр по дате + **"Все города"** в верхней части — см. 6.1.0.
- Счётчик уведомлений (колокольчик с бейджем количества) в правом верхнем
  углу — не описан в исходном тексте ТЗ. Указывает на необходимость
  системы уведомлений (например: новые возвраты, заказы зависшие в одном
  статусе долго). **Не специфицировано в ТЗ как функциональное
  требование** — реализовать как минимум визуальный элемент-плейсхолдер,
  логику уведомлений вынести в отдельное обсуждение, не блокировать ей
  остальную разработку.
- KPI-карточки с цветными иконками-бейджами (корзина/доллар/сумка/график) —
  чисто визуальное решение, см. раздел 10.
- Миниатюры товаров в "Последние заказы" — см. 6.1.2.
- "Топ товаров" в компактном виде (без выручки/количества, только прибыль) —
  см. 6.1.3.
- Блок "Финансы за месяц" без отдельной карточки "Закупки" — см. 6.1.4 и
  открытый вопрос №9.
- 4 быстрых действия вместо 5 — см. 6.1.5 и открытый вопрос №10.

### 13.2 Экран "Заказы"
- Карточный вид заказов с миниатюрой товара и полем "Цвет" — см. 3.3,
  6.2.1.
- Иконка-шеврон `>` справа у каждой карточки — открывает детальную
  карточку заказа (подразумевает отдельный экран/модалку "Детали заказа",
  не описанную отдельно текстом в исходном ТЗ, но логически необходимую
  для просмотра/редактирования полей закупки, логистики и audit log
  конкретного заказа — реализовать как часть раздела 6.2, отдельной
  спецификации не требует, поля те же, что в 3.5).
- Сводная строка "Всего заказов / На сумму / Прибыль" под списком —
  см. 6.2.1a.
- Иконка фильтра (воронка) в правом верхнем углу как альтернативный
  доступ к фильтрам, дублирующий чипы под поиском — чисто UI-решение,
  не влияет на состав фильтров из 6.2.2.

### 13.3 Экран "Возвраты"
- Третий статус возврата "Отменён" — см. 3.6.1, расширение диаграммы
  переходов в 4.2, BR-9.
- Чипы быстрого фильтра по статусу (Все/На возврате/Возвращён/Отменён) —
  см. 6.3.1.
- Фильтр "Причина" как отдельный выпадающий список — означает, что хотя
  причина возврата вводится свободным текстом (6.3.2), наиболее частые
  причины должны быть доступны для последующей фильтрации (например,
  список уникальных значений, которые уже встречались в базе, а не
  фиксированный enum) — реализовать как фильтр по списку уже введённых
  в системе значений причин.
- Карточка возврата с миниатюрой и вариантом/цветом товара — согласуется
  с 3.3.
- Сводная строка "Всего возвратов / На возврате / Возвращено" —
  см. 6.3.4 (примечательно: не включает "Отменено" в сводку — следовать
  макету, не добавлять самостоятельно четвёртую метрику).

### 13.4 Экран "Расходы"
- Поле "Способ оплаты" у каждого расхода + отдельный фильтр —

- Дополнительная иконка настроек-фильтров (две горизонтальные линии со

- Превью "Прибыль по товарам" (топ-5 с миниатюрами) со ссылкой

### 13.6 Сквозные наблюдения по всем экранам
- Все суммы — рубли с пробелом как разделителем тысяч и символом ₽ после
  числа (например "156 700 ₽") — соблюдать этот формат во всём интерфейсе.
- Все даты — формат ДД.ММ.ГГГГ, время отдельно через точку (например
  "15.07.2026 · 12:30").
- Номера заказов — формат "№XXXX" (четырёхзначные числа в макете,
  возрастающие).
- Статусы заказов и возвратов везде отображаются как цветные
  скруглённые бейджи (не текст обычным шрифтом) — см. таблицу
  соответствия цветов в финальном дизайн-промпте/референсах, не
  фиксируется жёстко текстом ТЗ.
- Нижняя навигация из 5 пунктов идентична на всех экранах: Главная,
  Заказы, Возвраты, Расходы, Отчёты — подтверждает, что это и есть
  основные верхнеуровневые разделы навигации приложения, без скрытых
  дополнительных разделов (настройки/пользователи доступны, по всей
  видимости, через другой путь навигации — например меню "···" в правом
  верхнем углу на Главной — не описанный отдельно текстом, см. также
  замечание про административные настройки в разделе 2.2).
